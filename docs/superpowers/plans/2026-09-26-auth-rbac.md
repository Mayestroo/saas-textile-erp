# Authentication and RBAC Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` to implement this plan task-by-task. Do not dispatch subagents. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver isolated platform and tenant authentication, refresh sessions, database-backed RBAC, login rate limiting, and protected tenant provisioning.

**Architecture:** Keep platform and tenant controllers, services, sessions, and permission guards in their existing `master/` and `tenant/` boundaries. Reuse small shared password, JWT-validation, API-error, and rate-limit primitives; query permissions and authoritative login counters from the correct PostgreSQL database on each request.

**Tech Stack:** NestJS 12, TypeScript 7, PostgreSQL 16, TypeORM migrations, `jose`, `argon2`, optional Redis via `ioredis`, Vitest, Supertest.

## Global Constraints

- Work only on `feature/auth-rbac`; existing branch was fast-forwarded to `main` using `--ff-only`.
- Keep Master and tenant authentication, sessions, and RBAC separate.
- Never trust request-body/query tenant IDs; resolve tenant login by hostname and protected requests by hostname plus verified JWT `company_id`.
- Never store plaintext passwords or refresh tokens. Password hashes use Argon2id; refresh hashes use SHA-256.
- PostgreSQL counters are the sole source of truth. Redis is an optional deny/cache accelerator and never stores authoritative counters.
- PostgreSQL counter increments are atomic and window state persists across Redis outages and recovery; database failure causes fail-closed `503`.
- Use only additive migrations; do not edit committed migrations or enable TypeORM `synchronize`.
- Do not implement models, workers, badges, Patta, sync, Patta varag'i, licensing workflows, payroll, reports, or Electron auth UI.
- All end-user errors are Uzbek Latin, structured, and do not reveal whether an email exists.
- Run real PostgreSQL integration tests only against the configured dedicated `_test` database and generated test tenants.

## Task 3: PostgreSQL-authoritative login rate limiter

**Interfaces:**

- `LoginRateLimiter.consume(dataSource, { scope, identifier, ipAddress, companyId? }): Promise<void>` increments account and IP buckets in a transaction and throws a structured `429` once either configured threshold is exceeded.
- Normalize the identifier before hashing; hash bucket dimensions and never persist raw email, IP, or password in the rate-limit table.
- A single `INSERT ... ON CONFLICT ... DO UPDATE ... RETURNING` per sorted bucket digest increments the current window or atomically starts a fresh window. Sorting digests before acquiring row locks avoids opposite lock order for concurrent requests.
- Expired buckets are removed by an indexed, bounded `DELETE` CTE using `ORDER BY expires_at LIMIT 100 FOR UPDATE SKIP LOCKED` before counter updates.
- Redis is not consulted in the current login decision path. This has the same safe outage/recovery behavior as an optional cache: no Redis state can override or reset PostgreSQL. PostgreSQL unavailable returns structured `503`.

- [x] Add unit tests for threshold, window reset, account/IP bucket denial, normalized identifiers, no raw identifiers in SQL parameters, PostgreSQL-only behavior when Redis is unavailable, and PostgreSQL unavailable.
- [x] Add PostgreSQL integration test launching concurrent `consume()` calls for the same account/IP and assert exact persisted attempts and the expected number of allowed/denied attempts.
- [x] Add recovery test: consume attempts, recreate the limiter after cache availability changes, and verify PostgreSQL window count and remaining lockout do not reset.
- [x] Run focused limiter unit and PostgreSQL integration tests; expected: concurrent calls produce no lost increments and bounded cleanup removes expired rows (6 unit, 12 Master DB, and tenant concurrency/window-reset integration tests passed).

## Task 4: Platform sessions, login, refresh, and RBAC

**Interfaces:**

- `PlatformAuthService.login({email,password,deviceId?})` returns only access/refresh tokens and safe user identity; invalid email/password/blocked user all return the same `INVALID_CREDENTIALS`.
- `PlatformAuthService.refresh(refreshToken)` validates platform refresh claims, locks the session row, rotates its hash, revokes on reuse, and rejects revoked/expired sessions.
- `PlatformAuthGuard` verifies platform access claims, checks ACTIVE user and unrevoked/unexpired platform session in Master, then attaches `PlatformPrincipal`.
- `PlatformPermissionGuard` requires `@PlatformPermissions(...codes)` and queries `platform_user_roles → platform_role_permissions → platform_permissions` in Master.
- Platform JWT payload includes `sub`, `scope=platform`, `session_id`, unique `jti`, `iss`, `aud`, `iat`, `exp`; it must not include `company_id`.

## Task 5: Tenant sessions, hostname resolution, login, and RBAC

**Interfaces:**

- `MasterTenantReader.findTenantBySlug(slug)` returns the same validated metadata shape as `findTenantById()` and returns only a matching ACTIVE company with encrypted connection metadata for authentication.
- `TenantResolverService.resolveForLogin({ hostname })` extracts a valid slug and resolves the Master company before asking `TenantConnectionManager` for its database.
- Existing `resolve({ hostname, authenticatedCompanyId })` remains mandatory for protected requests and rejects a slug/company mismatch.
- `TenantAuthService.login({ hostname,email,password,ip,deviceId? })` uses the resolved tenant DataSource, consumes its PostgreSQL rate limit, verifies an ACTIVE tenant user, and returns tenant-only claims with verified company ID.
- `TenantAuthGuard` verifies tenant access claims, enforces hostname/company match, ACTIVE user/session state, and attaches `TenantPrincipal`, company context, and tenant DataSource.
- `TenantPermissionGuard` queries only `users → roles → role_permissions → permissions` in the verified tenant DataSource.
- `TenantRbacService.grantRolePermissions()` accepts only codes in the canonical `TENANT_PERMISSION_SEEDS` allowlist and verifies those codes exist in that tenant's `permissions` table; it cannot access Master platform-permission storage.
